# Планирование траекторий и контроль столкновений (M5)

**Тема:** моделирование и симуляция робота-манипулятора для сортировки объектов по цвету  
**Статус:** базовый модуль M5; проверяет кинематическую/геометрическую допустимость плана, но не исполняет его динамически.  
**База реализации M5:** `02_Спецификация/параметры_системы.yaml`, версия `M5-v1.1`. Сквозная интеграция M7 проверена на SSOT `M7-v1.5`; наружная ширина лотков увеличена до 184 mm, координаты слотов и проверенные waypoint не изменялись (см. `01_Управление/приемка/M07.md`).

## 1. Назначение и границы

Планировщик получает только валидированные записи `DetectionBatch` интерфейса M4, текущие четыре координаты руки, положение захвата и явный список доступных мест укладки, переданный вызывающей стороной. Он либо возвращает полный план «подход → захват → подъём → перенос → укладка → освобождение → отход → возврат в безопасную стартовую позу», либо структурированный отказ с кодом, фазой и диагностикой.

Успех `PlanResult` означает, что весь сгенерированный путь прошёл IK, проверку суставных/временных ограничений и дискретную проверку столкновений до первого действия захвата. Это не означает, что объект был захвачен или отсортирован. Динамическое исполнение, контактная устойчивость, сила захвата, слежение за траекторией и безопасное восстановление интегрированы позже в M7 и проверены в пределах выбранных виртуальных сценариев; итоговая сквозная приёмка и статистическая кампания остаются за M9. Тесты M5 подтверждают только подсистему планирования; физический прототип отсутствует.

## 2. Поток данных и граница истинных данных

```text
M4 DetectionBatch estimates ─┐
current q / gripper state ───┼─> Planner ─> PlanResult / safe refusal
caller supplied free slots ─┘                 │
                                               ├─ Cartesian waypoints + IK branch
                                               ├─ q(t), dq(t), ddq(t), gripper(t)
                                               ├─ phase/event labels
                                               └─ sampled collision/clearance record
```

Для рабочей геометрии планировщик использует оценённые `track_id`, класс, координаты XY в BASE, yaw, confidence, uncertainty, validity и время M4. Габарит целевого объекта берётся из SSOT по проектной модели. Положение всех collision proxies перед каждым расчётом перезаписывается оценками M4; MuJoCo `qpos0`, внутренний цвет/ID объекта и истинная поза объекта не используются как вход контроллера. Идентификаторы объектов в верификаторе служат только для сопоставления M4-треков с однотипными collision proxies. Эталонная истинная поза допустима независимому оценщику, но отсутствует в интерфейсе planner.

`UNKNOWN` можно учитывать как препятствие при валидной геометрической оценке, но такой объект нельзя выбирать целью захвата. Устаревший, невалидный или неоднозначный трек делает карту препятствий неполной и приводит к безопасному отказу.

## 3. Контракт планировщика

Основной интерфейс: `planning.planner.Planner.plan_cycle(batch, target_track_id, current_q, current_gripper_m, available_slot_ids, now_time_s, sample_step_override_m=None)`.

`available_slot_ids` обязателен и принадлежит вызывающей логике будущего M6; ожидаемый формат `COLOR:index` (`RED:0..2`, `GREEN:0..2`, `BLUE:0..2`). Planner проверяет геометрию конкретного места, но не резервирует его, не отслеживает occupancy и не изменяет состояние партии.

Результат `PlanResult` содержит:

- `SUCCESS` и неизменяемый `Plan` только после проверки полного цикла;
- иначе код отказа, текст причины, фазу и диагностику; `plan=None` при любом отказе.

Основные коды: `INVALID_BATCH`, `INVALID_INPUT`, `STALE_DETECTION`, `UNSUPPORTED_CLASS`, `SCENE_UNCERTAIN`, `NO_AVAILABLE_SLOT`, `SLOT_INVALID`, `TARGET_OUT_OF_SCOPE`, `IK_UNREACHABLE`, `NEAR_SINGULARITY`, `BRANCH_DISCONTINUITY`, `COLLISION_AT_START`, `COLLISION_GRASP`, `COLLISION_PATH`, `COLLISION_PAYLOAD`, `NO_DETERMINISTIC_ROUTE`, `VERTICAL_PATH_ERROR`, `VELOCITY_LIMIT`, `ACCELERATION_LIMIT`, `TIMEOUT`, `SCENE_CAPACITY_EXCEEDED`.

`Planner.replan(...)` отбрасывает прежнюю геометрию плана, принимает свежие M4 данные и текущее q, после чего повторно проверяет новый полный цикл. Он не продолжает старую траекторию по устаревшей цели.

## 4. Фазы, waypoint и события

| Фаза | Геометрическое действие | Состояние объекта/захвата | Контактная политика |
|---|---|---|---|
| `INITIAL_APPROACH` | Подъём TCP из текущей безопасной позы | объект свободен, пальцы открыты | обычные зазоры |
| `ORIENTATION_ALIGN` | Переориентация на безопасной высоте | без контакта | обычные зазоры |
| `PREGRASP_ROUTE`, `PREGRASP` | Движение над оценённой XY целью | объект свободен | обычные зазоры |
| `DESCENT` | Вертикальный Cartesian descent | пальцы открыты | запас для пальцев к цели не менее M5 порога |
| `GRASP_CLOSE` | Закрытие до геометрически рассчитанной ширины | объект пока свободен | разрешён контакт пальцев с выбранной целью |
| `LIFT` | Вертикальный подъём | на событии `OBJECT_ATTACHED` прокси следует TCP | только фазовые контакты выбранных пальцев/груза |
| `TRANSFER`, `PREPLACE` | Перенос по проверенному радиальному маршруту | груз следует TCP | остальные объекты и окружение остаются активными |
| `PLACE_DESCENT` | Вертикальный descent к выбранному месту | груз захвачен | разрешено опирание груза на полку места |
| `RELEASE` | Открытие захвата | переход `carried` → `placed` на `OBJECT_RELEASED` | разрешён контакт груза с полом своего места |
| `RETREAT`, `SAFE_RETURN` | Вертикальный отход и возврат на безопасной высоте | объект установлен | рука и установленный груз остаются проверяемыми |
| `SAFE_HOME` | Возврат к исходной безопасной конфигурации | груз остаётся неподвижным в месте | обычная проверка, с явной поддержкой груза |

События плана: `GRIPPER_CLOSE_COMPLETE`, `OBJECT_ATTACHED`, `RELEASE_BEGIN`, `OBJECT_RELEASED`. Это временные метки/метаданные плана, а не реализация FSM и не доказательство физического удержания. `Plan.phases`, `Plan.waypoints`, `Plan.samples`, `Plan.events`, `Plan.slot_id`, `Plan.selected_ik_branch`, длительность и диагностика доступны будущему M6/M7.

Поза захвата использует оценённые XY/yaw и центр объекта из геометрии M2. `pregrasp/lift/place/retreat` строятся на зафиксированной safe-TCP высоте. Вертикальные участки задаются в Cartesian пространстве, а перед временной параметризацией дополнительно проверяется FK: XY не изменяются, yaw постоянен в пределах численного допуска M3/M5. Точное размещение центра, ширина захвата и высоты берутся из SSOT.

## 5. IK, ветви и непрерывность

1. M3 аналитическая IK возвращает допустимые решения обеих локтевых ветвей и симметричные ориентации квадратного объекта.
2. На старте planner определяет текущую elbow branch. В одном плане ветвь фиксирована; переключение ветви без допустимого непрерывного перехода через сингулярность запрещено.
3. Для целевой позы рассматриваются все допустимые ориентации симметрии текущей ветви, а не первый элемент списка IK.
4. Стоимость выбора складывает dimensionless L2 расстояние суставов, нормированное на characteristic spans M3, и SSOT-вес обратной manipulability/singularity penalty. Radians и meters напрямую не смешиваются.
5. Каждый Cartesian участок адаптивно дробится по максимальному линейному шагу, угловому шагу yaw и нормированному шагу суставов. Проверяются реальные joint limits M3; периодический unwrap не может пересечь физические границы шарниров.
6. Порог `planning.minimum_abs_sin_q2` применяется как запрет на построение waypoints вблизи сингулярности; диагностический код отличается от столкновения.

В M5 систематически проверяются оба IK branch-кандидата для эквивалентной позы. Полный рабочий цикл строится из фактической стартовой конфигурации SSOT и не перескакивает между ветвями. Конкретный выбор branch и все изменения настройки сохранены в JSON результата.

## 6. Детерминированная стратегия пути

Используется детерминированная стратегия для заявленной статичной ячейки: безопасный подъём, переориентация, движение по радиальному transfer ring на высоте M2 safe-transfer, вертикальный descent, перенос, вертикальная укладка и безопасный возврат. Радиус ring равен `max(r_start, r_goal) + planning.transfer_ring_radial_clearance_m`, ограничивается достижимой невырожденной областью и проверяется FK/IK/коллизиями. Три перехода (к объекту, к месту, обратно) могут выбирать короткую/обходную дугу; варианты перечисляются детерминированно.

M5 не добавляет RRT/PRM/OMPL. Проверки показывают, что для указанных и проверенных областей ячейки детерминированный маршрут предоставляет допустимые планы; если конкретная оценка цели, загруженность/clearance препятствий или branch-continuity не допускает маршрут, результат — safe refusal. Это не обещание пройти любую конфигурацию препятствий и не гарантия достижимости любой точки, проверенной только по TCP в M3.

## 7. Временная параметризация

Геометрический путь и время его исполнения разделены. Waypoints внутри семантической фазы параметризуются shape-preserving PCHIP-кубическим spline в нормированных суставных координатах вместе с шириной пальцев; на границах фаз/событий используется quintic rest-to-rest закон с нулевыми скоростью и ускорением. Контактные участки получают масштаб скорости из SSOT. Время фазы рассчитывается из аналитических верхних границ производных spline и лимитов скорости/ускорения M2 плюс SSOT 2% temporal reserve.

Для каждого отсчёта сохраняются `q`, `dq/dt`, `d²q/dt²`, координата/скорость/ускорение пальцев, TCP FK, фаза и clearance. Отсчёты проверяются на суставные ограничения и лимиты скорости/ускорения; превышение ведёт к отказу. Скорость/ускорение TCP и yaw-rate дополнительно вычисляются по аналитической FK chain rule; они проверяются против консервативной огибающей, выведенной из M2 длин звеньев и суставных лимитов. Отдельные Cartesian actuator caps в M2 не заданы: эти огибающие — кинематические границы, а не новые спецификации приводов. Максимальный шаг траекторной дискретизации ограничивается консервативной оценкой максимального перемещения любой точки collision geometry между соседними отсчётами, включая переносимый объект.

Временная модель — геометрическая командная траектория. Она не моделирует tracking error, actuator torque, упругость, backlash, динамику контакта и реальное время выполнения на прототипе.

## 8. Политика столкновений

### 8.1. Проверяемые тела

- все активные collision geoms основания/звеньев/оси Z/запястья/пальцев;
- self-collision всех межзвенных пар, кроме ровно шести задокументированных механически соседних пар из `collision.allowed_pairs`;
- стол/рабочая поверхность, стены лотков и другие статические collision geoms модели M2;
- все валидные M4 объекты, не являющиеся целью, с размерами из общей модели M2;
- выбранная цель при свободном состоянии, переносе и укладке;
- переносимый объект против руки, стола, лотков и остальных объектов.

Проверка повторяется для каждого отсчёта временно параметризованного плана, после сглаживания пути. Конечные точки сами по себе не считаются доказательством.

### 8.2. Broad/narrow phase и смысл clearance

Для каждого отсчёта строятся консервативные AABB geoms. AABB-gap быстро исключает геометрически удалённые пары только если нижняя оценка больше их индивидуального требуемого запаса. Близкие/возможные пары передаются в MuJoCo `mj_geomDistance`, результат которой является signed minimum distance и ограничивается сверху `distmax`. M5 задаёт `distmax=0.05 m`; поэтому `narrowphase_minimum_m_capped` — ближайшая узкофазная signed-distance среди проверенных близких пар с потолком 50 mm, а не полный unbounded глобальный минимум.

`clearance_lower_bound_m` — консервативная оценка нижнего предела зазора среди всех пар текущего отсчёта: AABB gap для исключённых узкой фазой пар и signed narrow-phase расстояние для проверенных пар. План отдельно сохраняет профиль этого показателя по времени. Положительная нижняя оценка и отсутствие нарушений относятся к проверенным дискретным конфигурациям; это **не непрерывная математическая гарантия** между образцами. Все систематические маршруты проверяются на SSOT baseline 1 mm; тот же центральный маршрут сравнивается с уточнённым шагом 0.5 mm. Сходимость для safety decision оценивается по совпадению результата preflight (нет новых столкновений/отказов на уточнённой сетке) и стабильности геометрического TCP пути. Сам минимум `clearance_lower_bound_m` является сеточно-зависимым диагностическим значением: его величина может измениться, когда более частая сетка попадёт ближе к локальному минимуму. Такое изменение сохраняется и анализируется, а не маскируется допуском; требования к каждой паре учитывают собственный clearance, swept-step bound и численный резерв на каждом sample. Отдельный тонкий статический obstacle между двумя свободными endpoint-конфигурациями должен вызывать collision в midpoint.

Официальный API MuJoCo описывает `mj_geomDistance` как подписанное минимальное расстояние, ограниченное `distmax`; он возвращает ровно cap, если меньшего расстояния не найдено. Поэтому cap и AABB lower bound фиксируются в SSOT и явно сопровождают отчёты. M5 не трактует дистанцию с cap как точное значение сверх 50 mm. [MuJoCo API: `mj_geomDistance`](https://mujoco.readthedocs.io/en/stable/APIreference/APIfunctions.html#mj-geomdistance).

### 8.3. Запасы и допустимые контакты

| Класс пары | Требуемый запас/правило |
|---|---|
| Робот–статические препятствия | 5 mm статического запаса + фактическая верхняя граница swept sampling + 0.25 mm численного резерва |
| Самостолкновение несоседних звеньев | 0 mm произвольного статического резерва + swept sampling + 0.25 mm численного резерва; контакт/проникновение отвергаются |
| Робот/переносимый груз–воспринятые нецелевые объекты | 15 mm; включает 5 mm статического, 2 mm XY uncertainty allocation, 3.5 mm поворотный сдвиг угла квадратной детали при 10°, 0.5 mm tracking allocation, 1 mm swept bound, 0.25 mm численный допуск и остаточный reserve |
| Пальцы–цель до закрытия | SSOT 4 mm grasp-entry порог; применяется только к выбранной цели на участке открытого подхода |
| Контакт закрытых пальцев с целью | разрешён только в перечисленных SSOT фазах захвата/переноса/укладки; signed проникновение больше 0.25 mm отклоняется |
| Цель–поверхность стола/лотка | разрешён только явно обусловленный контакт опоры на захвате/укладке; все остальные пары остаются проверяемыми |

Разрешение контакта не отключает геометрию выбранного объекта целиком: только конкретные пары пальцев/объекта, только именованные фазы; корпус захвата, ладонь, запястье и нецелевые объекты продолжают проверяться. Основание/стол крепятся одним явно перечисленным контактом. Остальные активные self-collision пары не выключаются.

## 10. Проверки и доказательства

Воспроизводимые файлы M5 находятся в `05_Верификация/planning/`:

- `cases/systematic_cases.json`, `tables/systematic_planning_results.csv` — детерминированные M4-интерфейсные положения, цвета, yaw, варианты obstacles и ответы planner;
- `cases/<case>/plan_result.json` — входы, версия/хеши, полный список waypoints/events и summary `PlanResult`; длинные массивы точек не дублируются;
- `trajectories/<case>.csv` — канонический полный machine-readable `q(t)`, суставные и TCP скорости/ускорения, события, фазы и clearance по каждому отсчёту;
- `plots/<case>/` — PNG/SVG графики суставов, скоростей, ускорений, clearance lower bound и TCP XY path с основными фазами цикла;
- `collision/sampling_convergence.json` — одна и та же задача на SSOT baseline 1 mm и уточнённом шаге 0.5 mm; отдельно показывает совпадение решения о столкновениях и сеточную чувствительность численной clearance-оценки;
- `collision/thin_obstacle_test.json` — endpoint-valid / midpoint-collision контролируемый тест тонкого препятствия; он повторяется также как тест `unittest`;
- `negative/negative_planning_cases.*` — safe refusal, включая недостаточный clearance до воспринимаемого препятствия;
- `reports/m5_validation.json`, `reports/M05.md` — сводка и ограничения;
- `04_Программа/planning/tests/` — unittest проверки планировщика, spline и collision policy.

Позитивные сценарии строят полный цикл для центра, левого/правого положения, ненулевого yaw, верхнего края области и двух дополнительных воспринимаемых объектов. Негативные тесты модуля дополнительно проверяют UNKNOWN, устаревшую M4-позу, uncertainty выше бюджета, неполную obstacle map, отсутствие доступных slots, выход из области и препятствие, нарушающее clearance. Ни один отказ не содержит `Plan`.

## 11. Ограничения и передача следующему этапу

- Ручной radial-ring planner — ограниченная, детерминированная стратегия, а не универсальный planner в configuration space. Не прошедшая полный preflight цель отвергается.
- Только статичные сцена и M4 snapshots; нет движущихся препятствий, частичного нового кадра посреди плана или динамического replanning во время контакта.
- Прокси объектов — одинаковые проектные кубоиды из SSOT; разнообразные формы, кучи и штабелирование не входят в модель.
- План — бездинамическая temporal parameterization по заданным пределам; силы/контакты и отслеживание проверяются только в будущих M7 virtual runs.
- Clearance — дискретно выборочная и ограниченная MuJoCo distance query/AABB оценка; непрерывная collision-free гарантия не заявляется.
- M5 не реализует FSM, reservation lifecycle, контроль захвата, retry/recovery или сортировку партии (M6).

Будущий M6 получает `PlanResult`, полный план фаз/waypoints/samples/events, `slot_id`, длительность и диагностику; сам collision path не пересчитывает. Будущий M7 получает `q(t)`, ограничения скорости/ускорения, ожидаемые clearance и фазовые события, но обязан отдельно проверить динамическое исполнение. M9 использует machine-readable логи и run hashes, однако M5 subsystem cases не являются итоговой кампанией эффективности сортировки.
